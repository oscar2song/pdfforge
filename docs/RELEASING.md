# Releasing PDFForge

This guide explains how to create a Release using the manual GitHub Actions workflow with safety checks. The workflow is designed to ensure releases only happen when you explicitly initiate them and basic quality gates pass.

Workflow file: `.github/workflows/release.yml`

## Overview

- Trigger: Manual only (`workflow_dispatch`)
- Required inputs when running:
  - `tag` (string): Target tag to release (e.g., `v2.2.1`)
  - `confirm` (string): Must be exactly `YES` to proceed
  - `draft` (boolean): Create the Release as a draft first (default: `true`)
- Safeguards enabled:
  1) Second confirmation input (`confirm = YES`)
  2) Draft by default (`draft: true`)
  4) SemVer validation for `tag` (supports optional pre-release suffix like `-rc1`)
  6) Smoke tests gate: sets up Python 3.12, installs deps, runs `pytest -q`
  8) Idempotency guard: if a Release for the tag already exists, creation is skipped
- Additional behavior:
  - Tag existence check (the tag must be pushed to the repo)
  - Docker image build (verification only; image is not pushed)
  - Autogenerated release notes
  - `prerelease: true` automatically if the tag contains a hyphen (e.g., `v2.2.1-rc1`)

## Prerequisites

1. Ensure all changes to be released are merged to the target branch (typically `main`).
2. Create and push a SemVer tag:

```bash
# Example for a final release
git tag v2.2.1
git push origin v2.2.1

# Example for a pre-release
git tag v2.2.1-rc1
git push origin v2.2.1-rc1
```

Notes:
- `tag` must match `vMAJOR.MINOR.PATCH` with optional `-PRERELEASE` (e.g., `v1.0.0`, `v1.2.3-rc1`).
- The tag must exist in the remote repository before running the workflow.

## Step-by-step: Run the Release workflow

1. Go to GitHub → Actions → `Release` workflow → `Run workflow`.
2. Fill inputs:
   - `tag`: e.g., `v2.2.1`
   - `confirm`: type `YES` (uppercase, exact)
   - `draft`: leave as `true` to create a draft (recommended) or set to `false` to publish immediately
3. Click `Run workflow`.

The workflow will:
- Verify `confirm` is `YES`.
- Validate the SemVer format of `tag`.
- Verify the tag exists in the repository.
- Set up Python 3.12, install dependencies, and run `pytest -q`.
- Build a Docker image tagged `pdfforge:<tag>` for verification.
- Create a GitHub Release with autogenerated notes (Draft by default). If a Release for this tag already exists, it will skip creation.

## Publishing drafts

If you created a Draft release (`draft: true`):
- Review the automatically generated notes on the Releases page.
- Click `Publish release` when ready.

If you set `draft: false` at dispatch time, the Release will be published immediately upon workflow success.

## Pre-releases

- If your tag includes a hyphen (e.g., `v2.2.1-rc1`), the workflow sets `prerelease: true` automatically.
- Use this for release candidates or beta/alpha versions.

## Common errors and fixes

- Error: `Confirmation failed. You must type YES to proceed.`
  - Cause: `confirm` input not set to `YES`.
  - Fix: Re-run the workflow and set `confirm` to `YES` exactly.

- Error: `Invalid tag format: ...`
  - Cause: `tag` does not match SemVer pattern `vMAJOR.MINOR.PATCH` (optional `-pre` suffix).
  - Fix: Use a valid tag like `v2.2.1` or `v2.2.1-rc1`.

- Error: `Tag <tag> not found.`
  - Cause: Tag not pushed to remote.
  - Fix: `git push origin <tag>` then re-run the workflow.

- Tests fail in `pytest -q` step
  - Cause: A regression or missing test dependency.
  - Fix: Fix code or add required test dependencies. If tests need extra packages, add them to `requirements.txt` or extend the workflow’s install step (e.g., `requirements-dev.txt`).

- Release already exists
  - Behavior: The job prints `Release for tag <tag> already exists. Skipping creation.`
  - Fix: If you need to update an existing Release, edit it directly in GitHub or delete it and re-run the workflow.

## Tips and recommendations

- Recommended flow: always run with `draft: true`, review notes, then publish.
- Keep `CHANGELOG.md` updated before tagging to ensure high-quality autogenerated notes and manual context.
- Consider protecting Releases with an Environment approval gate if your org requires it.
- Optional enhancement (not enabled): add a `dry_run` input to run build/tests without creating a Release.

## Example inputs

- Final release:
  - `tag`: `v2.2.1`
  - `confirm`: `YES`
  - `draft`: `true` (recommended) or `false`

- Pre-release:
  - `tag`: `v2.2.1-rc1`
  - `confirm`: `YES`
  - `draft`: `true`
